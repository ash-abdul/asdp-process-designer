# ASDP Process Designer

> **Phase:** 0 — Architecture & Specification
> **Status:** documentation only. No application code, no dependencies, no framework scaffolding.
> **Last updated:** 2026-08-22

The ASDP Process Designer is an AI-assisted, requirements-driven process-engineering
application. It transforms unstructured and structured business inputs into a governed,
traceable, validated, executable **Camunda 8 Process Application**.

It is **not** a BPMN drawing tool and does not replace Camunda Modeler.

---

## The one-paragraph description

Business inputs arrive in whatever form they exist — BRDs, SOPs, policies, spreadsheets,
screenshots, diagrams, legacy BPMN. AI reads and reconciles them into a **structured,
traceable requirement model** in which every statement is linked back to the exact page,
cell, or region it came from, and in which extracted fact, AI interpretation, AI
recommendation, and human-approved requirement are never confused with one another.
Humans resolve the gaps, ambiguities, and conflicts that AI surfaces, and approve the
result. Only then is a **technology-neutral Business Process Specification** produced, and
only after that is approved are **BPMN, DMN, Camunda Forms, and integration contracts**
generated by deterministic compilers. Generated artifacts are immutable outputs that users
review but never hand-edit. The validated result is packaged as a Camunda-ready Process
Application and handed off; after handoff, Camunda owns technical refinement and ASDP never
overwrites it.

```
Source Material
  → AI Requirement Understanding
    → Structured Requirements ── [human approval gate]
      → Business Process Specification ── [human approval gate]
        → BPMN / DMN / Forms / Integration Specs   (generated, immutable)
          → Validation ── [human approval gate]
            → Camunda-ready Process Application ── [human approval gate]
              → Handoff (Camunda becomes source of truth)
```

---

## Binding principles

These are not preferences. They are the load-bearing constraints of the product, and every
document in `docs/` is consistent with them.

1. **Requirements-driven.** Users modify requirements and approved semantic specifications.
   They do not structurally edit generated BPMN, DMN, or Forms.
2. **Generated artifacts are immutable outputs** of a versioned generation process.
3. **AI assists understanding; deterministic code owns governance.** AI never writes to the
   repository, never emits artifact serialisations, and never approves anything.
4. **Nothing exists downstream without provenance.** Every requirement traces to source
   evidence or is explicitly marked as inference.
5. **No silent conversion.** Vague or incomplete requirements cannot become executable BPMN;
   approval gates block the path structurally, not by convention.
6. **Provider-neutral AI.** The application depends on an AI Provider Abstraction, never on
   a single vendor API.
7. **Bilingual by construction.** Arabic and English are first-class from the data model up.
